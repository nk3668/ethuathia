## Summary
Build the Smithy nodes from town trees v4 that need something the sim or the Prepare screen doesn't do yet.

| Node | Effect | Row |
|---|---|---|
| Maker's Marks I–III | +8% chance per rank to identify gear on pickup | Tier I row 1 |
| Artisan Implements / Tailored Attire (pick one) | Each class's starting main-hand / defensive piece upgrades to that class's own Tier-1 item | Tier I row 2 |
| Forge Stamps / Apprentice Trinket (pick one) | Keen, Warding and Nimble stamps assigned per adventurer on Prepare, with class defaults / a class-matched ring or amulet for everyone | Tier II row 6 |
| Field Salvage Kit | Opt-in on Prepare: overloaded adventurers break unwanted plain gear into weightless scrap worth at-risk Trophies; never upgrades or enchanted items | Tier II row 6 |

## Why
Gemini's rework made Smithy kits class-owned so casters benefit too (a staff or focus, not only a sword). That needs a per-class upgrade path in `ClassDef`, a per-adventurer loadout choice on Prepare, and a new AI inventory action.

## Acceptance criteria
- [x] Every class names its Tier-1 main-hand and defensive kit item in `ClassDef`; `validateContent` checks they exist and fit the class's gear.
- [x] Maker's Marks rolls on pickup with the seeded RNG, and an identified item logs and reveals as ETH-142 requires (no leak of unidentified state).
- [x] Forge Stamps: the Prepare loadout step lets each adventurer pick a stamp (defaulting by class); random recruits get the default. Apprentice Trinket picks the class-matched jewelry.
- [x] Field Salvage Kit is a Prepare toggle; when on and overloaded, the baseline AI salvages the lowest-value plain item instead of dropping it, and the scrap's Trophies join the at-risk total.
- [x] Codex, tooltip and log text for each. Balance: T0 identity (20 seeds) and one all-nodes-on smoke run; the per-node T2 sweeps are left to the M2 capstone, ETH-161 (Nate's policy change, 2026-11-25).

## Notes
- If the Prepare loadout step proves big, split Forge Stamps into its own item at the planning gate.

## Refined plan (planning gate, 2026-11-24)

Studied against real code on main (ETH-132 and ETH-159 merged). Grid cells (`src/content/town/smithy.ts` header): Maker's Marks row 1 col 1; Artisan / Tailored row 2 cols 0 and 1 (pick one, `exclusiveGroup: 'smithy.tier2'`); Forge Stamps / Apprentice Trinket row 6 cols 0 and 1 (pick one, `'smithy.tier6'`); Field Salvage Kit row 6 col 3. Prerequisites (`requires`) are not in the spec: proposed Maker's Marks `[]`, Artisan / Tailored `[upgrade.fitted_straps]`, Forge Stamps / Trinket `[upgrade.scroll_case]`, Field Salvage Kit `[upgrade.assayers_ledger]`. Costs are placeholders for ETH-161.

### 1. Maker's Marks I-III (no new sim code)
- `tryIdentifyOnPickup` (`src/sim/items/effects.ts`) already rolls the Wits `identify` stat (percent stat, capped `SKILL_CAP` 95) on `state.rng.loot`, once per instance (`identifyTried`, ETH-142), and goes through `identifyItemFor`, which emits `itemIdentified` and reveals the item. So the node is a ranked party bundle: `{ kind: 'bundle', scope: 'party', bundle: { modifiers: [{ stat: 'identify', op: 'add', value: 8 }] } }`, `ranks: { max: 3, costGrowth: 1.6 }`, tags `identify`, `numeric`. The stat tooltip credits "Maker's Marks" for free (`upgradePartyBundles`).
- Spec/code conflict: spec says "gear". The roll covers every unidentified item picked up (gear, jewelry, potions, scrolls). Resolution: accept that and word the tooltip "items"; restricting it would need a new per-category modifier for no gain.
- Files: `src/content/town/smithy.ts` (+ export in `town/index.ts` if nodes are listed there). Tests: a ranked-node test that the `identify` stat rises by 8 per rank with the node credited; a fixed-seed pickup test (hand-built map, unidentified plain gear, `identify` forced to 100 by a bundle) that the item reveals with the usual log and that an unidentified item's `identified: false` state never shows before the roll.

### 2. Artisan Implements / Tailored Attire
- Content: no "Tier-1 item" concept exists, so add one pair of defs per class (8 new `ItemDef`s in `src/content/items.ts`, or a new `src/content/kitItems.ts` if items.ts passes ~800 lines; it is 672 now): Vanguard mace -> `item.flanged_mace` (exists; damage +3, accuracy -1 stays as is) and shield -> new *Kite shield* (armor 2); Outrider dagger -> new *Hunter's dirk* (damage 2, accuracy 1) and boots -> new *Rider's boots* (evasion 2); Lorekeeper staff -> new *Ironbound staff* (damage 2, evasion 1) and jerkin -> new *Scholar's coat* (armor 2); Reaver hatchet -> new *Bearded axe* (damage 3) and cap -> new *Iron helm* (armor 2). Numbers are a starting shape for ETH-161.
- `ClassDef.kitUpgrade?: { weapon: string; defense: string }` (`src/content/classes.ts`; schema, `refs` for the two ids, and a `check` that each exists, is gear, shares a slot with the kit's main-hand item / first armor item (the same two pieces `giveKit` already treats as `weapon` / `defense`), and differs from the base piece; a class that has a `kit` must have a `kitUpgrade`).
- New start perk `{ perk: 'tier', piece: 'weapon' | 'defense' }` in `src/content/startPerks.ts` (reuse the `START_ENCHANT_PIECES` pair, renamed `START_KIT_PIECES` with the old name kept as an alias). `upgradeStartConfig` -> `RunConfig.kitTier?: StartKitPiece[]` (`ItemsConfig`). `giveKit(entity, classId, enchant, tier)` swaps the named piece's def for the class's `kitUpgrade` before creating the kit item; the existing `enchant` (+1) then applies to the swapped item, so it stacks with Runed Implements / Warded Attire. Kit mark and "never sold" are unchanged (`newKitItem`).
- Spec/code conflict: the existing kit-pieces for a class already are "Tier 0"; the upgrade must stay a pick-one so a profile owns at most one. Conflict with the item-reachability check (`tools/content-reachability.ts` demands a loot entry or a recover contract): resolution is to give the new defs no `loot` entry (adding loot shifts the loot table and breaks T0 identity for every run) and teach the check that class kits (`kit`, `kitUpgrade`, `trinket`) are a source.
- Tooltips: `describeStartPerk` (`src/meta/grantText.ts`) gains a `tier` line ("Starting main-hand items are upgraded to each class's own Tier-1 item"); the Prepare "From the town" list picks it up through `describeGrant`. Log: `kitIssued` (logText/run.ts:74) already names the pieces issued, so it shows the upgraded names; add a line for upgraded pieces only if that message does not already read well.
- Tests: `validateContent` fixtures for the new check (unknown id, wrong slot, missing upgrade); `giveKit` per class with each perk (right def, still `kit`, never sold, enchant stacks); `upgradeStartConfig` fixed order.

### 3. Forge Stamps / Apprentice Trinket
- Stamps reuse existing special enchantments (`enchant.keen` accuracy +1 on weapons; `enchant.nimble` evasion +1 and `enchant.warding` status resist +10 on armor, `src/content/enchantments.ts`), applied at level 1 as `enchantments: [{ id, level: 1 }]` on the kit piece. New small content table `src/content/stamps.ts` (`FORGE_STAMPS`: id `keen | warding | nimble`, enchantment id, piece `weapon | defense`, name, text; refs validated) and `ClassDef.stamp` (the class default: proposed Vanguard warding, Outrider nimble, Lorekeeper warding, Reaver keen; open question). Keen goes on the kit's main-hand item, Warding and Nimble on the kit's first armor piece (the same `defense` piece as the enchant perk). Kit pieces stay identified, so nothing hidden is created.
- Perk: `{ perk: 'stamps' }` -> `RunConfig.stamps?: true` (the node only unlocks the choice). Per adventurer: `AdventurerConfig.stamp?: StampId` (`src/sim/state.ts`). `giveKit` takes the member's stamp (ignored if `RunConfig.stamps` is not set).
- Prepare: `RecruitPick` (`src/meta/prepare/party.ts`) gains `stamp: StampId | null` (null = class default; the zod `pickSchema` makes it `.nullable().default(null)` so saved Prepare choices from before still load, no slice migration); `fillParty` writes the resolved stamp (pick, else the class's default) into each `AdventurerConfig` only when the node is owned, drawn without touching `rng` (so recruit draws, names and T0 hashes stay put). `PartyPanel` shows a "Stamp" select per slot (Class default first, then the three, each with an `Explain` link) only when the node is owned; the preview line mentions it. The slot is the adventurer (there is no roster until M5/M7, records are issued per run by `startRun`), so "per adventurer" means per party slot.
- Spec/code conflict: spec says random recruits get the class default; that needs the class known at build time, which `fillParty` has after drawing the class, so the stamp is resolved there.
- Recommendation on splitting: keep Forge Stamps in this item. It is one select, one schema field and one config field, smaller than the sim work for Field Salvage Kit. Split only if the generic Prepare toggle from ETH-187 is not merged when this item starts, and then split Field Salvage Kit, not the stamps.
- Apprentice Trinket: `ClassDef.trinket?: string` (a ring or amulet def; validated as jewelry that fits a free slot with the kit), start perk `{ perk: 'trinket' }` -> `RunConfig.trinket?: true`, `giveKit` issues it as a kit item (identified, never sold). Proposed pairs from existing defs (no new items): Vanguard `item.copper_band` (HP), Outrider `item.knotwork_pendant` (evasion), Lorekeeper `item.hearthstone_amulet` (HP, MP), Reaver `item.garnet_signet` (HP, damage). Rings sit in `ring1`; `slotFor` handles it.
- Tooltips/Codex/log as above (`describeStartPerk` cases for `stamps` and `trinket`; stamp names are the existing enchantment Codex entries; the Prepare panel text names the choice).
- Tests: stamps per class and per slot with the fixed seed, default for random recruits, saved-choice load without `stamp`, `kitIssued` log text, trinket per class.

### 4. Field Salvage Kit
- Toggle (reuse from ETH-187): needs a generic "opt-in owned node on Prepare" mechanism. Interface needed: (a) a way to mark an `UpgradeNodeDef` as toggleable (for example `toggle: { default: false }`) and a validated Prepare choice section (for example `toggles`, in `RUN_CHOICES`, holding the set of node ids switched on, with a schema that drops ids the profile does not own); (b) a helper `toggledOn(profile, choices, nodeId): boolean`, true only if the node is owned and on; (c) a Prepare panel that lists owned toggle nodes with a checkbox, label, tooltip and the node's `describeGrant` text; (d) a place for `buildRunConfig` to map "on" nodes to config (a `toggle` start perk handled by `upgradeStartConfig`, or `apply` per toggle). I will add `RunConfig.salvage?: true` and a `{ perk: 'salvage' }` start perk and plug into whatever shape ETH-187 lands. Until it merges this node can't be finished, so order: ETH-187's toggle first, or this part last. If ETH-187 slips, I would ship a minimal toggle section myself, but only after checking with you (two designs would collide in `RUN_CHOICES`).
- Sim: new item request `salvage { index, qty? }` (`src/sim/items/actions.ts`, cost like `drop`, validate: the run has `salvage`, entry exists, `canSalvage`); `canSalvage(state, item)` = gear def (weapon, armor, jewelry), weight above 0, not `kit`, not a relic, **already identified** and plain (no `enchant`, `enchantments`, `blessing`), and not a clear upgrade (`upgradeSlot(...) === null`). Unidentified gear is never salvaged: the AI cannot know if it is enchanted, and choosing among unidentified items by their hidden state would leak it (ETH-142/147; add this rule to the hidden-state AI guard in `docs/ARCHITECTURE.md` §11.6 and the contract/property test).
- Instead of a weightless scrap item, scrap is a tally: event `itemSalvaged { actor, item, name, qty, value, floor, pos }` and a tracker `track.salvage` (`src/sim/run/trackers.ts` style) with state `{ value }` whose `rewards` give `{ trophies: floor(value / VALUE_PER_TROPHY) }`, so the Trophies join the run's at-risk total (the 25% wipe loss applies, per CLAUDE.md §3) and nothing is left in the pack. Rate is the same as the exit sale (`VALUE_PER_TROPHY`, 1 Trophy per 10 value) so salvaging neither beats nor loses to carrying it out, except that it frees the weight and survives a wipe at 75%. Rounding is once, over the sum, like `itemSale`.
- AI: new rule action `act.salvage_lowest` in `src/sim/items/rules.ts`: `resolve` takes `lowestValueIndex(...)`; if that entry `canSalvage`, return `{ request: { id: 'salvage', index, qty }, detail: 'breaking down the <name> for scrap...' }` (same qty arithmetic as `act.drop_lowest`), else `null`. Baseline row `{ cond.overloaded -> act.salvage_lowest }` is inserted between `act.equip_upgrade` and `act.drop_lowest` in `ITEMS_BASELINE_URGENT`; with the flag off `resolve` returns `null` and the rule never fires (T0 identity expected). `wantsItem` is unchanged, so there is no pickup churn.
- Spec/code conflict: the Omen multiplier applies to at-risk currency as it is earned (CLAUDE.md §3), but "Trophies converted on the way out are not multiplied, so hoarding loot can't inflate an Omen run". In-run salvage is closer to the second case. Resolution to confirm: salvage Trophies stay in the at-risk total (spec) but are excluded from the Omen multiplier; Omens (ETH-067 / M2.2) are not built yet, so this item adds a note to ETH-067's Log and a `multiplied: false` hint on the tracker reward, or leaves that to M2.2 if no such field exists.
- UI/log: `src/ui/shell/logText/` line "Mira breaks the bent helm down into scrap (+N value toward Trophies)"; the run summary's Trophies breakdown gets a "salvaged" line from the tracker extras; Codex/tooltip text on the toggle and the new rule action (the Library will list it in M3).
- Tests: a hand-built map with an overloaded adventurer carrying plain identified gear (salvaged, tally and event right), enchanted/unidentified/kit/upgrade items (dropped instead), the flag off (dropped, identical to today), wipe loses 25% of the salvage Trophies, determinism, a `Rng`-free check (no new randomness).

### Cross-cutting
- `RunConfig` additions: `kitTier`, `stamps`, `trinket`, `salvage`, and `AdventurerConfig.stamp`; `checkRunConfig` validates stamp ids and class pieces. Saves: `RunConfig` is not persisted across versions; `prepare` slice stays v1 (only an optional field). Contract and property guards (§11.6): extend for the new `Effect`-free perks, the new rule action's hidden-state rule, and the new `{ perk }` kinds (`startPerkSchema` discriminated union).
- Size: **M, upper end** (about 4 content files, 8 items, 3 sim files, 4 meta files, 2 UI files, ~12 test files). Order of work, each its own commit: Maker's Marks; class kit upgrade + items; trinket; stamps (meta + UI); salvage (blocked on the ETH-187 toggle).
- Balance: all four are balance-affecting (gear stats, identify chance, carry). **T0** (20 seeds) with nothing owned must show 0 hash diffs against main (new items have no loot entries, the new rule never fires, the new fields default to unset). **T2** (100 seeds, `--seeds 100`): the harness takes `--upgrades id1,...` (`tools/headless/args.ts`), so measure on vs off with the same seeds and preset by buying one node at a time (plus its prerequisites in both arms): arm A = prerequisites only, arm B = prerequisites + the node (Maker's Marks at rank 3; Artisan; Tailored; Stamps with class defaults; Trinket; then all together). Salvage needs a harness switch for the toggle (`--toggles id,...`, added with the toggle or here), and only matters for runs that become overloaded, so also report how many salvage events per run. Record depth, win/retreat/wipe split, deaths by cause, items picked up, Trophies per run, with the commit hash, in the Log; every delta is explained, no new stalls. No T3 (the M2 capstone, ETH-161, checks the bands).
